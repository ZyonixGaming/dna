Abstract

This thesis describes the structure of the genome in Horsey Game: a set of 240 genes, each carried on two strands, each resolving to one of four alleles, and each contributing to a single decoded phenotype. It sets out the storage format, the property table that gives every gene its per-allele values and its blending weight, the two accessors that read a gene, the canonical order of the genes and the groups they fall into, and the effects each group has on the creature. It covers the allele-level rules that test the sorted dominant and recessive arrays rather than the blended value, the colour and pattern systems that give the coat its appearance, the feature flags that record binary traits, the locomotion signal system that coordinates limb movement, and the genome hash that seeds per-horse randomness. It is written for anyone who needs to understand what a gene is, how to read one correctly, and what each one does.

Chapter 1: The Genome and Its Genes

A Horsey genome is a fixed-length sequence of genes. It is not a variable collection and it is not a hierarchy; it is an array of exactly 240 entries, each indexed by a small integer, and every creature in the game carries the same 240 entries in the same order. What differs between creatures is the allele each entry holds, and the property table that turns that allele into a number.

This chapter describes the physical storage of the genome: how the 240 genes are held in memory, how a raw byte becomes an allele index, and how the two copies of each gene are sorted into the arrays that some rules read instead of the blended value.

1.1 Two Strands of 240 Genes

Each creature carries two strands. The strands are stored contiguously in the creature's entity structure, one after the other, each 240 bytes long and each an array of signed bytes:

StrandEntity offsetSizeElement type
Dominant strandentity + 0x2B8240 bytesint8_t
Recessive strandentity + 0x3A8240 bytesint8_t

The total genome size is therefore 480 bytes. The two strands are storage labels only; as Section 1.3 explains, the blend that produces a gene's value is based on the numerically higher and lower allele indices, not on which strand a byte came from.

When the game decodes a genome, it copies both strands into a single contiguous 480-byte local buffer. The first 240 bytes are one strand and the second 240 bytes are the other. The two accessors described in Chapter 3 take a pointer to this buffer and a gene index, and read the two alleles from buffer[gene] and buffer[gene + 0xF0].

On disk the layout is different. A save file packs both alleles of a gene into a single byte as n2 * 8 + n1, using 1-based indices into the gene's own nucleotide order. That is 240 bytes, not 480. The in-memory layout described here is what the decoder sees after the save has been unpacked. Both descriptions are correct at their own layer.

1.2 Allele Normalization

Each raw gene byte is normalized to an allele index in the range 0..3. The normalization is a positive modulo operation:

allele = (byte % 4 + 4) % 4

The observed implementation uses the bitmask x & 0x80000003 followed by a sign correction for signed characters. The result is always one of four values, regardless of the raw byte's sign or magnitude. Only four allele indices exist per gene, and every rule that reads an allele reads one of those four numbers.

1.3 Allele Ordering and the Sorted Arrays

For each gene, the two normalized allele indices are sorted into a high and a low value. The decoder builds two derived arrays immediately after copying the genome: a dominant array holding the smaller of the two allele indices for each gene, and a recessive array holding the larger. The terminology is slightly counter-intuitive: the dominant allele is the one with the lower index, and the recessive allele is the one with the higher index.

typedef struct HorseAllelesHiLo {
    uint8_t hi[240];
    uint8_t lo[240];
} HorseAllelesHiLo;

typedef union HorseAlleles {
    uint8_t sorted[480];
    HorseAllelesHiLo rank;
} HorseAlleles;

The flattened representation is:

  • sorted[0..239]: greater allele index for each gene
  • sorted[240..479]: lesser allele index for each gene

The loop that fills these arrays is a pair of conditional moves off a single comparison, so the two arrays are genuinely min and max, gene by gene. Most genes are read through the blended value described in Chapter 3, but a small number of rules test the sorted arrays directly. Those rules are the subject of Chapter 9.

The decoding scratch area also contains a 16-entry coat palette used during colour processing:

typedef struct HorseDecodeAlleleScratch {
    HorseColor coat_palette[16];
    HorseAlleles alleles;
} HorseDecodeAlleleScratch;

1.4 Chromosomes and the Gene Map

The 240 genes are grouped into 20 chromosomes, numbered 00 through 19. Each chromosome has a fixed length, and the lengths sum to 240:

10, 13, 13, 15, 11, 8, 11, 8, 11, 11, 13, 15, 13, 11, 11, 13, 15, 11, 11, 16

A GENE_MAP[helix][position] table gives the canonical gene index for each position on each chromosome. The map is a permutation: every gene index from 0 to 239 appears exactly once, and the position of a gene on a chromosome has no relationship to its index in the canonical order.

On disk, a genome is written as 40 lines of HH:SEQUENCE, with each chromosome appearing twice in a row — once per strand. The sequence is one nucleotide per gene, and the nucleotide's index within the gene's own ordering (Section 2.5) is its allele.

Chapter 2: The Gene Property Table

A gene on its own is just an index. The meaning of a gene — what it does, how its alleles differ, and how strongly one allele dominates the other — comes from a property table. That table is the single most important data structure in the genome system, and it is populated at runtime from genes.xml.

2.1 The genes.xml Schema

genes.xml holds all 240 genes in canonical order. Each entry has six attributes:

AttributeMeaning
nameThe gene's name, matching the G_* identifiers used throughout this thesis.
mBlend weight, as a percentage applied to the lower allele.
sScale divisor. The final value is the blended raw value divided by s.
g0–g3Raw value for each allele index. g0 is the value when the allele is 0, and so on.
nPer-gene nucleotide ordering: a permutation of ACGT. The index of a letter within this string is its allele number, and lower index is dominant.

An example entry:

<gene name="SIZE" m="95" s="100" g0="100" g1="50" g2="35" g3="75" n="ATGC" />

Here SIZE has a blend weight of 95, a scale divisor of 100, raw values of 100, 50, 35, and 75 for alleles 0 through 3, and a nucleotide ordering of A, T, G, C. A creature carrying the nucleotide A on both strands has allele 0 on both, which resolves to a raw value of 100 and a final value of 1.0.

2.2 The Blend Weight

The m attribute is a percentage that determines how much weight the lower allele receives when the two alleles differ. A value of 100 means the lower allele's value is used exclusively. A value of 50 means the two alleles contribute equally. A value of 0 would mean the higher allele is used exclusively, though no gene in the table has that value.

Of the 240 genes, 190 have m = 100, meaning they are fully dominant: the lower allele's value is used and the higher allele is ignored for the blended result. The remaining 50 genes are genuinely blended, and their values depend on both alleles.

Because the blend direction is always the same — m weights the lower allele and 100 - m weights the higher — a gene with m = 100 short-circuits to the lower allele's value. That is the most common case, and it is why so many genes behave as though only one of the two alleles matters.

2.3 The Scale Divisor

The s attribute divides the blended raw value to produce the final value used by the phenotype. Most genes have s = 1 or s = 100:

  • s = 1 for 143 genes. These genes use their raw values directly.
  • s = 100 for 94 genes. These genes store their values as percentages or as centi-units, and divide by 100 to get a fraction.
  • s = 10 for 3 genes. These are intermediate scales.

The scale divisor is applied after blending. A gene with s = 100 and raw values of 100 and 50 produces a blended raw value of 75 when both alleles contribute equally, and a final value of 0.75.

2.4 Per-Allele Values

The four g attributes give the raw value for each allele index. The values are not sorted; they follow the gene's own logic. For a gene like TAIL_EXISTS, the values might be 1, 0, 1, 2 — meaning allele 0 gives a normal tail, allele 1 gives no tail, allele 2 gives a normal tail, and allele 3 gives two tails.

For a gene like SIZE, the values are 100, 50, 35, 75 — four different sizes, with the allele index determining which one applies. Because lower index is dominant, an allele pair of 0 and 3 blends toward the allele 0 value.

2.5 Nucleotide Ordering

The n attribute is the bridge between the letters in a genome sequence and the allele indices used by the property table. Each gene has its own ordering, and the index of a letter within that string is its allele number.

For SIZE, n="ATGC" means A is allele 0, T is allele 1, G is allele 2, and C is allele 3. For ASPECT, n="GCAT" means G is allele 0, C is allele 1, A is allele 2, and T is allele 3. The two genes have different orderings, and a global mapping from letters to alleles would be wrong for at least one of them.

This is per gene, not global. Do not assume that A always means allele 0. Read the n attribute for the gene you are working with, and use n.indexOf(letter) to get the allele index.

2.6 The Runtime Table Layout

At runtime, the property table is an array of 240 entries, each 32 bytes:

struct GeneProperties {
    uint32_t gene_id;      // +0x00  must equal its own index, else an assertion fires
    int32_t  base_value;   // +0x04  blend weight, 0..100
    uint8_t  unknown[8];   // +0x08  name pointer or reserved bytes
    float    values[4];    // +0x10  one per allele, already divided by the scale
};

The total size is 4 + 4 + 8 + 16 = 32 bytes, and 240 * 32 = 7680 bytes for the whole table. Before using an entry, the decoder verifies that GENE_PROPS[gene_index].gene_id == gene_index. A mismatch triggers an assertion, which is how a corrupted or misaligned table is caught.

The values[4] array holds the per-allele values already divided by the s attribute, so the accessors in Chapter 3 do not need to apply the divisor themselves.

Chapter 3: Reading a Gene

Reading a gene means taking two allele indices and producing a single number. The game provides two accessors for this — one returning a floating-point value, one returning an integer — and they differ in more than their return type. Understanding both, and the traps in each, is necessary before any gene's effect can be predicted.

3.1 The Two Accessors

Both accessors take a pointer to the genome buffer and a gene index. They read the two alleles from the buffer, normalize them, sort them into high and low, retrieve the corresponding values from the property table, and blend them according to the gene's base_value.

The pseudo-code is the same for both:

base = GENE_PROPS[gene].base_value
hi   = greater allele index
lo   = lesser allele index

The two alleles are read from the two strands. The lower index is the dominant allele, and the higher index is the recessive allele. The blend weights the lower allele by base / 100 and the higher allele by 1 - base / 100.

3.2 The Floating-Point Blend

The floating-point accessor produces a value that can be fractional:

GetGeneFloat =
    (1.0 - base / 100.0) * GENE_PROPS[gene].values[hi]
  + (base / 100.0)       * GENE_PROPS[gene].values[lo]

The formula is a simple linear interpolation. When base = 100, the first term vanishes and the result is values[lo]. When base = 0, the second term vanishes and the result is values[hi]. For intermediate values, the result is a weighted average.

This is the accessor used by every gene that produces a dimension, an angle, a scale, or any other value that needs sub-unit precision.

3.3 The Integer Blend

The integer accessor produces a whole number:

GetGeneInt =
    (base * values[lo] + (100 - base) * values[hi]) / 100

At first glance this looks equivalent to the floating-point version scaled by 100. It is not, because of truncation. The integer accessor truncates each value to an integer before blending, and then truncates the result of the division. The floating-point accessor blends the values as floats and only truncates if the caller chooses to.

A gene read through the integer accessor is always 0 if its scale divisor is 100. The values[] array holds values that have already been divided by s. For a gene with s = 100, those values are fractions between 0 and 1, and truncating them to integers gives 0 for every allele. The blended result is then 0 for every genome. This is not a bug in the game; it is a consequence of the two accessors having different rounding behaviour, and it means that a gene's effect depends on which accessor reads it.

The integer accessor is used by genes whose values are naturally integers — counts, flags, and small enumerations. The floating-point accessor is used by genes whose values are dimensions or angles.

3.4 Traps in the Accessors

Two traps are worth stating explicitly, because both have misled analyses:

  • There is no special case for base_value == 100. The general form of the floating-point blend already yields values[lo] when base = 100. A port that adds a special case for 100 is not wrong, but it is not doing anything the general formula does not already do.
  • The integer accessor truncates before blending. A port that blends as floats and then truncates will produce different results from the game for any gene with fractional values. The difference is small for large values and total for values below 1.

Both traps are consequences of the same design: the two accessors are not two views of one function, they are two functions that happen to share a formula. Treating them as interchangeable produces errors that are invisible on most genes and obvious on a few.

Chapter 5: Structural Genes

The structural genes determine the creature's shape: its body dimensions, its posture, its limbs, its tail, its neck, and its head. They are the largest group and the one most responsible for the visible difference between creatures.

5.1 Body Dimensions and Posture

The body's size and shape come from a small set of genes that combine multiplicatively:

bones_scale_a = GetGeneFloat(G_BONES) + 1.0
bones_scale   = GetGeneFloat(G_BONES2) + bones_scale_a
giant_dwarf   = GetGeneFloat(G_GIANT_DWARF)
chest_small   = GetGeneFloat(G_CHEST_SMALL)
chest_big     = GetGeneFloat(G_CHEST_BIG)
size          = GetGeneFloat(G_SIZE)

body_area = (size + size) * bones_scale * chest_big * chest_small * giant_dwarf

skinny        = GetGeneFloat(G_SKINNY)
aspect_skinny = skinny * GetGeneFloat(G_ASPECT)
body_aspect   = (chest_small * aspect_skinny) / chest_big

The body's area and aspect ratio are then combined with the posture genes to produce width and height. The posture genes are G_BIPED and G_QUADRUPED, which select one of four body plans:

BipedQuadrupedBody planAspect handling
01Horseunchanged
00Rabbit1.5 / aspect, or aspect * 0.8 if NECK_ONTOP
10Human1.0 / aspect
11Centaurunchanged, plus a second torso

Once the aspect ratio has been adjusted, the body's width and height are:

body_width  = sqrt(body_aspect * body_area)
body_height = body_area / body_width

The final dimensions include a back offset that is non-zero only when the higher allele of CHEST_SMALL is 3, giving a sloped chest. That offset is capped at a quarter of the body's shorter side, and on a centaur it is further capped by the room left in front of the second torso.

5.2 Legs

The leg genes determine whether legs exist, how long they are, how thick they are, and how they bend. The core calculation is:

leg_type     = GetGeneInt(G_LEG_TYPE)
leg_enabled  = leg_type != 0
stretch_a    = GetGeneFloat(G_LEG_STRETCH) + 1.0
stretch_scl  = GetGeneFloat(G_LEG_STRETCH2) + stretch_a
leg_length   = GetGeneFloat(G_LEG_LENGTH) * stretch_scl
leg_thickness = GetGeneFloat(G_LEG_STRENGTH) * 0.16

If LEG_TYPE is 2, the leg becomes a square stub: both length and thickness are doubled, and the length is set equal to the thickness. This is the fixed-length stubby leg.

The leg's muscle-derived sizes are:

muscle_use = GetGeneFloat(G_MUSCLE_USE) * 100.0
leg_upper  = GetGeneFloat(G_LEG_STRENGTH) * muscle_use
leg_lower  = leg_upper * 0.6

For type 2, leg_upper is halved. The leg's angle comes from G_SPLAY, and its joint behaviour comes from G_LEG_JOINT_TYPE, G_LEG_FLEXIBILITY, and G_LEG_FLEX_BIAS. When the joint type is 2, the flex bias is added to the socket angle, giving a one-sided range.

Several leg genes are conditional. G_LEG_PENCIL overrides the leg's dimensions when it is positive, producing a thin, pencil-like leg. G_LEG_SKEW shears the lower half of the leg sideways, but only when the leg is not jointed. G_LEG_IS_CIRCLE turns the leg into a wheel when G_LEG_HAS_FOOT is 0 or G_FOOT_IS_CIRCLE is 0.

5.3 Arms

The arms follow the same pattern as the legs, using the G_ARM_* genes. Their length, thickness, muscle-derived upper and lower sizes, skew, hand flag, elbow range, and angles are calculated independently.

Two quirks are worth noting. First, the arm's length reads LEG_STRETCH and LEG_STRETCH2, not ARM_STRETCH and ARM_STRETCH2. The latter two genes are never read by anything. This is a copy-paste error in the game, and it is visible: a creature with a non-zero ARM_STRETCH2 does not have its arms stretched.

Second, ARM_NODE_SCALE scales the length of whatever stands in the front socket — an arm, or with ARM_TAG 1 a leg — and leaves its thickness alone. It reaches legs only, and it reaches the upper arms too, because each upper-arm record starts as a copy of the front socket's record.

5.4 Feet and Hands

The foot genes determine whether a foot exists, how large it is, whether it is circular, and whether it points backwards. The core calculation is:

has_foot   = GetGeneInt(G_HAS_FOOT)
feet_flag0 = has_foot > 0
feet_flag1 = GetGeneInt(G_FOOT_BACKWARDS) != 0

feet_x = FOOT_SIZE + leg_thickness + foot_clown_extra
feet_y = foot_toe * feet_gene89 + feet_x

If both the leg and foot are circular, the foot becomes a circle of radius equal to the foot's widest point. FOOT_BACKWARDS mirrors the foot about the limb's centreline; values 1 and 2 do the same thing, because the decoder collapses the gene to a boolean with a single != 0 test.

The hand genes follow the same pattern. HAND_WIDTH, HAND_LENGTH, and HAND_FINGER determine the hand's shape, and the hand is centred on the limb's centreline rather than flush with its edge.

5.5 Tail

The tail genes determine whether a tail exists, how long it is, how thick it is, and what shape it has. The core calculation is:

tail_exists = GetGeneInt(G_TAIL_EXISTS)
tail_size   = GetGeneFloat(G_TAIL_SIZE)
tail_length = GetGeneFloat(G_TAIL_SHORT) * tail_size
tail_base   = GetGeneFloat(G_TAIL_ASPECT) * tail_size
tail_style  = GetGeneInt(G_TAIL_SHAPE)

The tail's shape is one of several values. Shape 1 is a rectangle, shape 2 is a reverse triangle, shape 5 is a stubby square, and shape 6 is a decorative chain of tiles. Shape 5 is converted to shape 1 before use, with the length set equal to the base.

TAIL_SEGMENTS is gated on the tail's shape. It only takes effect when the shape is 1, and it divides the length only when the length is more than twice the base. On a triangle or a chromosome tail, the gene does nothing.

TAIL_EXISTS 2 produces two tails, not one longer one. The second tail is built at the same joint, ten degrees back, unless the socket's joint type is 2.

The tail's angle and joint position depend on QUADRUPED. A quadruped measures its tail off the rear top corner, with TAIL_BOTTOM moving it to the bottom when there is no derriere. A non-quadruped measures its tail off PAT_BELLY, a pattern gene used here as a fraction of the body's height.

5.6 Neck

The neck genes determine whether a neck exists, how long it is, how thick it is, and where it attaches. The core calculation is:

neck_enabled   = GetGeneInt(G_NECK_TYPE) != 0
neck_length    = GetGeneFloat(G_NECK_LENGTH) * (body_max_dim * 0.5)
neck_offset_x  = GetGeneFloat(G_NECK_GIRAFFE) + neck_length
neck_thickness = GetGeneFloat(G_NECK_THICKNESS)
neck_offset_y  = neck_thickness * (body_min_dim * 0.25)

The neck's joint position is adjusted by NECK_ONTOP, which slides it back along the spine, and by NECK_SLOUCH, which walks it down the front edge. Both are skipped on a centaur.

NECK_COCK adds to the neck's pitch: the stored angle is -90 - NECK_ANGLE - NECK_COCK, so the neck rises at the sum of the two angles. NECK_GIRAFFE is added in raw gene units after the length has been scaled by the body.

When NECK_JOINT_TYPE is 2, NECK_FLEX_BIAS is added to the socket angle, giving the neck a resting angle that differs from its gene values.

5.7 Head

The head genes determine the head's size, shape, and features. The core calculation is:

head_scale = GetGeneFloat(G_HEAD_SHRUNK) * GetGeneFloat(G_HEAD_GIANT)
head_area = ((G_HEAD_THICK_SKULL + G_HEAD_SIZE) * 0.33)
          * body_bone_scale * head_scale

head_aspect = G_HEAD_SQUARE
if head_aspect == 0:
    head_aspect = G_HEAD_ASPECT

head_width  = (G_HEAD_X_GROWTH + 1.0) * sqrt(head_aspect * head_area)
head_height = (G_HEAD_Y_GROWTH + 1.0) * (head_area / head_width)

The head's features — eyes, ears, mouth, jaw, tongue, and nose — each have their own genes and their own rules. The eye is two circles, with EYE_SIZE determining the eye's radius and PUPIL_SIZE determining the pupil's. The ear's position is determined by EAR_X, EAR_SIZE, and EAR_ASPECT, and its colour is determined by EAR_COMP, which is promoted by EAR_STYLE.

The nose's size is capped by the available span, which is (headHeight - mouthHeight) * MOUTH_Y. This means NOSE_Y cannot move a full-size nose at all, because the nose has already filled its span. The same NOSE_SIZE can produce noses of different sizes on different heads, because the span is head-relative and mouth-relative.

HEAD_JOINTED controls whether the head is rigidly attached to the neck or placed on an independent physics joint. For a still-frame renderer, the important consequence is that when HEAD_JOINTED is non-zero, the head's static cock angle is not baked into its position; it becomes a property of the joint instead.

    antler_width = 0;
    hat_width    = 0;

HAT_EXISTS only gates the hat's own size. A hat cannot exist without antlers, and the two genes are not independent. A creature with HAS_ANTLERS = 0 and HAT_EXISTS = 1 grows no adornment at all.

6.3 Antler Genes

The antler genes control the antler's size, shape, branching, and colour. ANTLER_W and ANTLER_H give the width and height of the root segment. ANTLER_TAPER controls how much the segment narrows toward its tip. ANTLER_POM adds a pom — a circle — at the tip when it is positive.

ANTLER_REC and ANTLER_REC2 cap the recursion depth for the back and front branches. ANTLER_MOD is a parity bitmask, not an enum: it is tested against (depth % 2) + 1, so a value of 1 branches at one depth parity, 2 at the other, and 3 at every depth.

ANTLER_FLIP negates the control record's angles between the back child and the front one, so a flip reaches the second child and everything under it but never leaks back up the tree. ANTLER_T1 and ANTLER_T2 are attach positions along the parent segment, not thicknesses; a value at or above 0.95 is treated as "at the tip".

6.4 Hat Genes

The hat genes control the hat's size, shape, and cloning. HAT_SIZE gives the hat's width, and HAT_ASPECT gives its aspect ratio. HAT_TAPER controls its taper, and HAT_POM adds a pom. HAT_POM_IS_LID converts the pom into a lid, setting it to 1 - taper when the pom is positive.

HAT_CLONE draws the whole segment twice, mirrored at ±clone * width / 2, but only at the root and only when HAT_TAPER > 0.1. A hat missing one of its two halves is this gene's effect.

The hat inherits ANTLER_COLOR from the antler record, which is why both render in the same colour. The hat also has its own back and front scales, angles, and angle jitter.

Chapter 7: Colour Genes

The colour genes determine the creature's coat, skin, and fixed colours. They are the most interconnected group in the genome: a colour is rarely the product of a single gene, and the order in which the genes are read is part of the specification.

7.1 Base Colour Selection

Base colour selection uses a dispatch on BASE_RED and BASE_GREEN, falling back to BASE_BROWN when both are 0. GREEN_KNOCKOUT disables BASE_GREEN entirely.

The dispatch carries four candidate colours, not two: a spot colour and three rungs of a ladder. The ladder is climbed by BASE_CREAM:

BASE_CREAMTakes
> 0.66The lightest rung
0.33 .. 0.66The middle rung
otherwiseThe darkest rung

Unset candidates hold a sentinel, opaque black, and are filled in from their neighbour afterwards: if (mid == sentinel) mid = dark, then if (light == sentinel) light = mid. Without that fixup, a default brown horse renders black.

7.2 Cream and the Ladder

The three rungs are the base colour, a middle shade, and a light shade. BASE_CREAM selects which rung becomes the base. The other two rungs are used by the pattern system and by parts that need a lighter or darker shade.

The ladder is one of the few places where a gene's value is a threshold rather than a multiplier. The thresholds at 0.33 and 0.66 divide the gene's range into three bands, and the band determines which rung is used.

7.3 White and Lethal White

WHITE forces the base colour to a hard-coded #dcdcdc, which is not a palette entry. When WHITE_IS_LETHAL is also set, the spot and alternate colours are washed out to the same value. The skin colour and the fixed colours (hoof, teeth, eye) are unchanged.

The effect is purely a slot overwrite with no geometric side effect. The pixel counts are byte-identical between WHITE = 0 and WHITE = 1 apart from the colour itself.

7.4 Skin Hue

Two genes form a 4-by-4 palette index:

skin_hue_index = allele(G_SKIN_HUE) + 4 * allele(G_SKIN_HUE2)

Separate low- and high-allele indices are calculated. The genome hash's low bit selects which one becomes the final skin colour. This is the mechanism behind the observation that skin is prone to random per-horse differences: two creatures with the same skin hue genes can have different skin colours if their genome hashes differ in the low bit.

7.5 Swaps and Overrides

Colour processing supports several swaps and overrides:

  • SWAP_BASE_SPOT exchanges the base and spot colours.
  • SWAP_ALT_SPOT exchanges the alternate and spot colours.
  • BASE_BLACK swaps base and alternate for every part except the torso, which keeps the pre-swap base.
  • AGOUTI restricts the black to the extremities when BASE_BLACK is also set.
  • BELLY_ALT recolours the upper limb to slot 2 or slot 1, depending on its value.
  • TAIL_ALT writes the tail's slot directly to 1 or 2.
  • FOOT_IS_HOOF sets the foot's slot to 4.
  • SKIN_HEAD sets the head and ear slots to 3, and at value 2 also the neck and the pattern remap.
  • SKIN_HANDS sets the hand's slot to 3, and at value 2 also the arm, leg, tail, and foot slots.

These overrides run in a fixed order, and later genes overwrite earlier ones. The order is load-bearing: a gene that writes slot 2 may be overwritten by a later gene that writes slot 3, and the final colour depends on which gene ran last.

7.6 Per-Part Slots

A part's colour is a slot index, not a colour role. Slots are resolved at the end, after all the swaps and overrides have run. This matters because swaps and BASE_BLACK move roles between slots: slot 2 is the black on one genome and the yellow on another. A tool that translates "slot 2" into a role name once, up front, silently picks the wrong one.

Three genes bend the slot index. RACCOON_EYE and EAR_COMP share a 4-by-3 remap. TAIL_ALT does not use the remap; it writes the tail's slot directly. BASE_BLACK puts the tail on slot 2 with or without AGOUTI.

Chapter 8: Pattern Genes

The pattern genes determine the coat's pattern: stripes, spots, perlin noise, and the belly band. The pattern is generated by a dedicated function that fills a grid of slot indices, one cell at a time, and the grid is then painted onto the torso.

8.1 The Pattern Fields

The pattern fields are read from a small set of genes:

pat_split       = GetGeneFloat(G_PAT_SPLIT)
pat_belly       = GetGeneFloat(G_PAT_BELLY)
gene193_any     = GetGeneInt(G_BELLY_ALT) != 0
pat_stripe      = GetGeneFloat(G_PAT_STRIPE)
pat_spot        = GetGeneFloat(G_PAT_SPOT)
pat_perlin      = GetGeneFloat(G_PAT_PERLIN)
pat_perlin2     = GetGeneFloat(G_PAT_PERLIN2)
pat_perlin_size = int(GetGeneFloat(G_PAT_PERLIN_SIZE))

Each field contributes to one of four scores, and the cell's slot is the index of the highest score.

8.2 The Grid

The grid's dimensions are derived from the body's size and aspect ratio:

cols = trunc( sqrt(ASPECT * SIZE) * 12 )
rows = max( 1, trunc( cols / body_aspect + 0.5 ) )

Because body_aspect is exactly bodyWidth / bodyHeight, dividing by it makes the cells roughly square whatever the body's shape. A normal horse gets a 16-by-9 grid; an alligator gets a 16-by-3 grid.

8.3 The Generator

The generator fills the grid by computing four scores for each cell and taking the index of the highest:

s[0] = 0.5                                              // the torso's own colour
s[1] = perlin(px, py, grad1) * PAT_PERLIN  + (stripe - spot)
s[2] = perlin(px, py, grad2) * PAT_PERLIN2 + x * PAT_SPLIT / cols
s[3] = 0.0                                              // never wins

stripe = PAT_STRIPE if (x % 2 == 0) else 0
spot   = PAT_SPOT   if (y % 2 == 0) else 0
belly  = 10.0 if PAT_BELLY <= y / rows else 0.0
s[ BELLY_ALT ? 2 : 1 ] = max(belly, s[ BELLY_ALT ? 2 : 1 ])

cell = argmax(s)

Three consequences fall out of this. First, PAT_SPOT needs PAT_STRIPE, because they share one score and spot enters it negatively; alone, -PAT_SPOT can never beat the 0.5 baseline. Second, PAT_SPLIT at 1.0 covers 43% of the grid, not half, because the term beats 0.5 only when x / cols > 0.5. Third, PAT_BELLY is a hard override, not a blend: 10.0 swamps every other score, so the belly band is solid.

8.4 The Noise Function

The noise is a textbook 2D Perlin with random unit gradients, except that the interpolator is a plain linear interpolation, not the usual 6t⁵ - 15t⁴ + 10t³ fade. That is what produces the faceted, blocky look of the coat.

The lattice size is:

gw = trunc(cols / psize) + 3
gh = trunc(rows / psize) + 3
psize = max(1, trunc(PAT_PERLIN_SIZE))

Two independent gradient fields are generated, one for PAT_PERLIN and one for PAT_PERLIN2, interleaved as grad1[i], grad2[i], grad1[i+1], .... Sampling is at x/psize + offX, y/psize + offY, where the two offsets are the first two random draws.

The result is offset by +0.5, so comparing against the 0.5 baseline means "noise above zero". A guard clamps the result to 0 if either intermediate falls outside ±10; it effectively never fires.

Chapter 9: Allele-Level Rules

Most genes are read through the blended value. A small number of rules read one of the two sorted allele arrays instead, and those rules behave differently from the blend. This chapter describes the arrays, the six tests that read them, and the two genes whose effects are entirely allele-driven.

9.1 The Dominant and Recessive Arrays

Immediately after copying the genome, the decoder builds two derived arrays:

dominant[i]  = min(strandA[i], strandB[i])
recessive[i] = max(strandA[i], strandB[i])

The names are slightly counter-intuitive: the dominant allele is the one with the lower index, and the recessive allele is the one with the higher index. The loop is a pair of conditional moves off a single comparison, so the two arrays are genuinely min and max, gene by gene.

9.2 The Six Allele Tests

There are exactly six tests in the decoder that read an allele rather than a value:

ArrayGeneEffect
RecessiveOSTO_SIZEScalloped spikes instead of triangles
DominantOSTO_SIZEForces OSTODERM to 2
RecessiveCHEST_SMALLThe sloped chest
DominantEYE_HUEEye styling
RecessiveAGOUTIThe ear's slot inside the AGOUTI branch
DominantGene 209Behaviour, not appearance

The predicate "recessive == 3" means "the higher allele is 3". The predicate "dominant == 3" means "both alleles are 3", because the dominant array holds the smaller of the two and it equals 3 only when both are 3. The two are not mirrors of each other, and a rule that reads one cannot be replaced by a rule that reads the other.

9.3 OSTO_SIZE

OSTO_SIZE is the clearest example of an allele-driven gene. Its two tests do different things:

if (recessive[OSTO_SIZE] == 3)  ostoderm_style = scalloped;
if (dominant[OSTO_SIZE] == 3)   OSTODERM = 2;

The first test makes the ostoderm's spikes scalloped rather than triangular. The second test forces OSTODERM to 2, which is the single big spike, even when OSTODERM itself is 0. The value written is a register left over from an earlier gene read; it happens to hold 2.

The practical consequence is that a creature carrying allele index 3 on both strands grows the single big spike even with OSTODERM at 0. This is not visible in the blended value, and a tool that reads OSTO_SIZE through the accessors will not see it.

9.4 CHEST_SMALL and the Sloped Chest

CHEST_SMALL's recessive test enables the sloped chest:

back = (recessive[CHEST_SMALL] == 3)
     ? min(bodyWidth - torso2Width, 0.25 * bodyMinDim)
     : 0;

The cap is the room left of the second torso, which is the whole body only when there isn't one. On a centaur, the chamfer is capped by the room in front of the main torso, not by the whole body. The sloped chest itself is a chamfer across the front-top corner, drawn as a triangle, with the strip behind it painted flat in slot 0.

Chapter 11: Locomotion Genes

The locomotion genes control how a creature moves. They do not affect its static appearance — a creature rendered in its build pose looks the same whether its locomotion genes are active or not — but once the physics simulation runs, they determine the gait, the timing, and the coordination between limbs. The locomotion genes occupy indices 0xDB through 0xEF, a contiguous block of 21 genes at the end of the canonical order.

This chapter describes the signal/react/event architecture that the locomotion genes implement, the five fields each node carries, the signal table that coordinates them, and the specific genes that populate those fields.

11.1 The Signal/React/Event Architecture

The locomotion system is a publish-subscribe network. Each node in the creature's skeleton can emit a signal on one of four channels, and each node can listen for signals on one of those channels. When a node hears the signal it is listening for, it switches its motor direction. There is no central gait controller; the gait emerges from the local interactions between nodes.

The architecture has three parts:

  • Signal groups. Each node that participates in locomotion is assigned an emit channel, numbered 1 through 4. When the node's joint reaches a limit, touches the ground, or a timer expires, it broadcasts on its channel.
  • Reactions. Each node can listen to one channel for fore-to-back motion and one channel for back-to-fore motion. The fore-to-back reaction is what makes a limb swing forward when another limb completes its backward stroke; the back-to-fore reaction is the reverse.
  • Events. A reaction is not enough on its own; the node must also specify which event on that channel triggers it. An event is one of four conditions: the joint hitting its back limit, the joint hitting its fore limit, the body touching the ground, or a timer expiring.

The result is a network in which each limb can be made to respond to any combination of conditions on any channel. The default gaits — walking, trotting, galloping — are produced by particular assignments of these five fields across the creature's nodes.

11.2 The Five Locomotion Fields

Each node has five locomotion fields:

FieldRoleExample
signal_groupEMIT channel (1–4) — this node broadcasts to this channelBack leg emits on channel 1
ftob_reactRECEIVE channel for fore-to-back motion"Listen to channel 2"
ftob_eventTRIGGER condition for ftob (1=back limit, 2=fore limit, 3=touch, 4=timed)"When that channel fires event 2"

btof_eventTRIGGER condition for btof"When that channel fires event 1"

The signal group is the channel a node emits on. The react fields are the channels a node listens to. The event fields are the conditions that must be true on the listened channel for the reaction to fire.

Channels are numbered 1 through 4. A node with signal_group = 0 does not emit; a node with react = 0 does not listen. The default baseline genome assigns the back leg to channel 1 and the front leg to channel 2, producing the alternating gait described in Section 11.7.

11.3 The Signal Table

Each physics tick, a 5-by-5 table is built:

signal_table[channel][event_type] = 0 or 1

The first index is the channel (0–4, with 0 unused). The second index is the event type (0–4, with 0 unused). The table starts all zeros and is filled by the emit pass.

The event types are:

EventCondition
1The joint hits its back limit
2The joint hits its fore limit
3The body touches the ground
4A timer expires (60 frames elapsed)

The table is rebuilt every tick. A signal emitted on one tick does not carry over to the next; the network is stateless between ticks, and the state that produces a gait lives in the joints' positions and the motors' directions.

11.4 The Emit Pass

The emit pass iterates every node with a non-zero signal_group. For each such node, it checks the node's joint against the four event conditions and sets the corresponding table entries:

if joint hits back limit:
    signal_table[signal_group][1] = 1
if joint hits fore limit:
    signal_table[signal_group][2] = 1
if body touches ground:
    signal_table[signal_group][3] = 1
if 60 frames elapsed:
    signal_table[signal_group][4] = 1

The emit pass does not care which node emits; it only cares about the channel. Two nodes emitting on the same channel produce the same table entries, and a listener on that channel cannot distinguish between them. This is what allows a single channel to coordinate multiple limbs: all the limbs that share a channel behave as one emitter.

11.5 The Consume Pass

The consume pass iterates every node with a non-zero react field. For each such node, it checks the two reaction channels against their event conditions:

if signal_table[ftob_react][ftob_event] == 1:
    switch motor to ftob direction
if signal_table[btof_react][btof_event] == 1:
    switch motor to btof direction

A node can have both a fore-to-back reaction and a back-to-fore reaction. If both conditions are true on the same tick, the second check overrides the first, because it runs after it. In practice, a well-formed gait avoids this by ensuring that the two conditions cannot both be true at once.

The consume pass is what turns the signal table into motion. A node that hears its trigger switches its motor direction, and the joint begins to move the other way. The next tick, the joint may hit its limit, which emits a new signal, which triggers another node, and the cycle continues.

11.7 An Example Gait

The default alternating gait is produced by assigning the back leg to channel 1 and the front leg to channel 2, with each limb listening to the other:

Back leg:
  signal_group=1          → emits on channel 1
  ftob_react=2            → listens to channel 2
  ftob_event=2            → when front leg hits its fore limit
  btof_react=2            → listens to channel 2
  btof_event=1            → when front leg hits its back limit

Front leg:
  signal_group=2          → emits on channel 2
  ftob_react=1            → listens to channel 1
  ftob_event=2            → when back leg hits its fore limit
  btof_react=1            → listens to channel 1
  btof_event=1            → when back leg hits its back limit

Trace one cycle:

  1. The back leg's joint hits its fore limit. It emits event 2 on channel 1.
  2. The front leg is listening to channel 1 for event 2. It switches its motor to the fore-to-back direction and begins to swing backward.
  3. The front leg's joint hits its back limit. It emits event 1 on channel 2.
  4. The back leg is listening to channel 2 for event 1. It switches its motor to the back-to-fore direction and begins to swing forward.
  5. The back leg's joint hits its fore limit again, and the cycle repeats.

The result is an alternating gait in which the two legs take turns. The gait is not programmed; it is a fixed point of the signal network. The genes set the channels and the events, and the physics produces the motion.

More complex gaits — trotting, galloping, bounding — are produced by different assignments. A trot pairs diagonal limbs on the same channel; a gallop puts the back legs on one channel and the front legs on another with different timing events. The architecture does not distinguish between these gaits; it merely provides the signalling primitives, and the gene values determine which gait emerges.

11.8 LOCO_SYNC

LOCO_SYNC is the final gene in the canonical order, at index 0xEF. It is a synchronisation gene that coordinates the locomotion system as a whole. Its exact effect is a global modifier on the timing of the signal network, and it is the only locomotion gene that does not belong to a specific limb group.

LOCO_SYNC is read through the integer accessor, and its allele values select from a small set of synchronisation modes. A value of 0 leaves the network unsynchronised; higher values introduce a global timing constraint that aligns the limbs' cycles.

The gene is the last one read by the decoder, which means it has access to every other gene's value through the phenotype. A tool that reads it independently of the rest of the locomotion block will miss its interactions with the signal and react genes.

Chapter 12: The Genome Hash

Every creature has a genome hash: a 32-bit value computed from the genome's bytes. The hash is used to seed the random number generator, which in turn drives the pattern generator and any other random decisions. It is also the source of the low bit that selects the skin hue.

12.1 The Hash Function

The hash is calculated over the genome bytes beginning at index 3. It runs two passes of 40 iterations, processing six bytes per iteration:

hash = 0
ptr = &genome[3]

for pass in 0..1:
    for i in 0..39:
        a = 1139564289 * (ptr[-2] + 1)
          + 65599 * (ptr[1] + 1
          + 65599 * (ptr[0] + 1
          + 65599 * (ptr[-1] + 1)))
        b = ptr[-3] + 1
        c = ptr[2]
        ptr += 6
        hash = c + 1 + 372007231 * b + a - 701829503 * hash

The result is stored as a 32-bit unsigned integer. Its low bit selects the low or high skin-hue index.

A second copy of this hash exists elsewhere, with an extra instruction that clears bit 28. That copy is not the genome hash. Applying the bit-clearing to the genome hash corrupts the result for roughly half of all genomes.

12.2 Seeding and Per-Horse Randomness

The genome hash seeds a global xorshift64 random number generator. The seed is the hash sign-extended to 64 bits; if the result is zero, the state is set to 1 instead. A separate saved-seed value allows the generator to be reset.

SeedRNG(s)  // s is the genome hash sign-extended to 64 bits
    saved = s
    state = (s == 0) ? 1 : s

ResetRNG()
    state = saved

next()
    x ^= x << 13
    x ^= x >> 7
    x ^= x << 17
    state = x

rand01()
    return (next() & 0xFFFF) / 65536

rand(lo, hi)
    return rand01() * (hi - lo) + lo

The random number generator is a single shared stream. The coat pattern is the first thing to draw from it — the seed is set at the top of the part builder and nothing consumes the generator before the torso is built. Anything else random about a creature, such as the angle jitter on antlers and hats, draws from the same stream afterwards. Consumption order is part of the specification: reproducing any later consumer requires reproducing every earlier one.

Two creatures with the same genome have the same hash, the same seed, and the same random sequence. Two creatures with different genomes have different hashes, different seeds, and different random sequences. The hash is the bridge between the genome and every random decision the creature makes.

Chapter 13: From Genome to Phenotype

The phenotype is the decoded result of the genome: a structure containing all the blended and derived values that the rest of the game consumes. This chapter describes the flow from raw genome to phenotype and the layout of the phenotype itself.

13.1 The Processing Flow

The processing flow is:

Raw genome: 480 bytes
  dominant strand at entity + 0x2B8
  recessive strand at entity + 0x3A8
        |
        v
Copy both strands into a local 480-byte genome buffer
        |
        v
Normalize each byte to an allele index in 0..3
        |
        v
Sort each gene pair
  high alleles -> scratch.alleles.sorted[0..239]
  low alleles  -> scratch.alleles.sorted[240..479]
        |
        v
Validate GENE_PROPS[gene].gene_id
        |
        v
Blend alleles with GetGeneFloat or GetGeneInt
        |
        v
Calculate body, limbs, joints, head, adornments,
colours, patterns, feature flags, ratios, and hash
        |
        v
HorseGenePhenotype

The decoder reads every gene in canonical order, from G_SIZE through G_LOCO_SYNC. Some genes are read more than once; some are read through the sorted arrays rather than the accessors. The order is fixed, and a few genes depend on registers left over from earlier reads.

The phenotype is a large structure. Confirmed offsets include:

The joint records are five in number, at +0x34 (tail), +0x80 (leg), +0xCC (arm), +0x114 and +0x15C (upper arms), and +0x1A4 (neck). Each is 0x48 bytes and holds the joint's existence flag, position, angle, tag, type, and range.

The colour array at +0x4E4 holds 20 ARGB values. The first four are the base, spot, alternate, and skin colours. The rest are fixed colours and overrides used by specific parts.

The pattern block at +0x534 holds the pattern fields, and the grid itself is allocated separately by the body builder.

The locomotion fields are populated from the locomotion genes and are consumed by the physics step, not by the static renderer. A still-frame renderer can ignore them entirely.

Chapter 14: If You Are Writing an Editor

This chapter collects the rules that matter when writing a tool that reads, writes, or renders a Horsey genome. Each one is a consequence of something in the preceding chapters, but each is worth stating on its own because each has been learned the hard way.

14.1 Ten Imperatives

  1. Read the n attribute. Each gene has its own nucleotide ordering. Do not assume that A means allele 0 for every gene. (Section 2.5.)
  2. Use the right accessor. The floating-point accessor and the integer accessor behave differently on fractional values. A gene read through the integer accessor is always 0 if its scale divisor is 100. (Section 3.4.)
  3. Check the allele arrays. Six rules test the sorted dominant and recessive arrays rather than the blended value. A gene that appears to do nothing through the accessors may be read through an allele array. (Section 9.2.)
  4. Do not assume a gene is independent. HAS_ANTLERS gates the hat. PAT_SPOT needs PAT_STRIPE. AGOUTI needs BASE_BLACK. Many genes only express when another is set. (Sections 6.2, 8.3, 7.5.)
  5. Respect the order of overrides. Colour slots are written by several genes in a fixed order, and later genes overwrite earlier ones. The final colour depends on which gene ran last. (Section 7.5.)
  6. Carry slots as numbers, not roles. A part's colour is a slot index, and swaps and BASE_BLACK move roles between slots. Translating a slot to a role name up front picks the wrong one on some genomes. (Section 7.6.)
  7. Reproduce the RNG order. The genome hash seeds a single shared random stream, and the coat pattern draws from it first. Reproducing any later consumer requires reproducing every earlier one. (Section 12.2.)
  8. Expect stale registers. Some genes are read through registers left over from earlier reads, and the result is not what the gene's value would suggest. OSTO_SIZE is the clearest case. (Section 9.3.)
  9. Treat fixed addresses as build-specific. The property table's address, the palette's address, and the decoder's address are all specific to one build of the game. Re-find them if the game updates. (Section 2.6.)
  10. Probe to verify, disassemble to derive. A probe answers "where does the ear sit" in twenty seconds; tracing it through the binary takes hours for the same answer. Conversely, no amount of capturing will reveal that the Perlin interpolator omits the standard fade curve. Use each for what it is good at. (Section 13.1.)

15.2 Implications

The genome system is more interconnected than it first appears. A gene is not an independent unit; it is one input to a decoder that reads all 240 genes in a fixed order, and some genes inherit state from earlier reads. A tool that treats genes as independent will be right about most of them and wrong about a few, and the few are the ones that produce the visible differences between creatures.

The distinction between the blended value and the allele arrays is the clearest example. Most genes are read through the accessors, and the accessors produce a weighted average of the two alleles. But six rules read the sorted arrays instead, and those rules see the alleles themselves, not their average. A tool that only implements the accessors will miss those six rules entirely.

The colour system is the second example. A part's colour is a slot index, and the slot is resolved at the end, after all the swaps and overrides have run. A tool that resolves slots early will pick the wrong colour on any genome where a swap or BASE_BLACK moves a role from one slot to another.

The locomotion system is the third. The locomotion genes do not set a gait directly; they set the channels and the events, and the gait emerges from the physics. A tool that reads the locomotion genes in isolation will see channel numbers and event types, not a walk cycle. The walk cycle is a property of the network, not of any single gene.

15.3 Future Work

  • The letter sequence of the chromosome tail. The base for each tile is read from a runtime array populated from in-game state that a still render cannot see. A tool must substitute a fixed sequence. (Chapter 5.)
  • The centaur's second torso. Its shape is the main torso's aspect ratio inverted, and its height matches the main torso's, but the formula is fitted rather than read. (Chapter 5.)
  • Circle tessellation. The game's circles are polygons, and coarser than a true circle. The difference is sub-pixel but visible in a pixel-level comparison. (Chapter 5.)
  • The systematic one-pixel height offset. Across a large sample, a port's silhouette is often exactly one row taller than the game's. The extra row accumulates somewhere in the head-and-neck chain. (Chapter 5.)
  • The antler on a second head. When a creature carries two heads and no main head, the first head's antler is roughly twice as long as the game's, while the second head's matches exactly. The cause is not yet understood. (Chapter 6.)
  • The eyebox's own clamp. The game pulls the eyebox up when its bottom would cross the mouth line and its right edge would cross the nose. The condition is located but not yet modelled. (Chapter 5.)
  • The exact effect of LOCO_SYNC. The gene is the final one in the canonical order and coordinates the locomotion network, but its precise interaction with the four limb groups is not yet fully traced. (Chapter 11.)

15.4 Final Remarks

The Horsey genome is a compact and well-structured system. Its 240 genes are enough to produce an enormous variety of creatures, and its property table makes the genes' effects transparent: each gene's per-allele values are stored in a single table, and the blend between two alleles is a simple weighted average.

The complexity comes not from the genes themselves but from the interactions between them. A colour is not one gene; it is a dispatch on three genes, a ladder climbed by a fourth, a set of swaps and overrides, and a final resolution that depends on the order in which everything ran. A pattern is not one gene; it is four scores computed per cell, with a noise function that is Perlin except for one detail. A head is not one gene; it is a dozen, each with its own preconditions and its own interaction with the others. A gait is not one gene; it is a network of signals and reactions, and the gait emerges from the network.

Understanding the genome means understanding both the parts and the connections. The parts are documented in the property table. The connections are documented in the decoder. This thesis has described both.
