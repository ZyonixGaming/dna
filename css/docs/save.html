Abstract

This thesis presents a complete structural, semantic, and reverse-engineered analysis of the Horsey Game save file format, designated save1.dat. The format is a tightly packed, version-dependent binary serialization of the entire game world, encompassing player state, equine genetics, location metadata, world items, and persistent progression counters. Through exhaustive corpus analysis of 148 save files spanning versions 8 through 12, disassembly of the Horsey executable (4,374,528 bytes, x86-64 PE), and controlled before/after experimentation, we establish a definitive reference for the format. Every byte from offset 0 to end-of-file is accounted for in the live reference save. We document the header and record table, the global player block, the RLE-encoded map, buried and world items, the indexed location array with its version-dependent slot count, stabled horse crowds, owner and champion genomes, Bookie records, the Bio-Hacker vat matrix, the 240-byte genome encoding, player inventory, Truck upgrades, and the horse detail block. We further provide a confidence taxonomy, a catalogue of corpus artifacts, and a set of editorial imperatives for any tool that reads or writes the format. This work is intended as a definitive companion for save editors, modders, and preservationists, and as a case study in the reverse engineering of bespoke game serialization.

Chapter 1: Introduction

1.1 Motivation

The Horsey Game save file, save1.dat, is the sole persistent artifact of a player’s entire career: their horses, their ranch, their progress, their world. Unlike many modern games that use standardized serialization frameworks (JSON, Protocol Buffers, SQLite), Horsey Game employs a bespoke, hand-rolled binary format that chains every block exactly, with no scanning, no padding, and no tolerance for desynchronization. This makes the format both fragile and fascinating: a single misplaced byte can crash the game on load, while a correct understanding allows complete mastery of the game state.

This thesis exists because the format was previously undocumented in its entirety. Earlier attempts at reverse engineering produced heuristic scanners that guessed at boundaries. Those scanners are now obsolete: every block in every walkable file is accounted for structurally. The confidence key in Section 1.3 distinguishes between STRUCTURAL (computed from the file itself), DERIVED (verified against an outside oracle), OPEN (located but not understood), and RE_CONFIRMED (verified by disassembling Horsey.exe). This thesis follows that taxonomy rigorously.

1.2 Corpus and Methodology

The corpus consists of every .dat file under the game’s save folder, versions 8 through 12: 148 files, of which 142 parse and all 142 walk end to end. Six files are known artifacts (Section 13.1) and are excluded from structural claims. The reference save is save1 - working.dat; the live save1.dat moves between sessions and is therefore not reproducible. The all-locations reference is locs-template.dat, a game-written v12 save holding all 34 location indices at once, each with its own proprietor, crowd and interior list. Statistics that no single file can establish—the crowd ranges in Section 6.10a, the attested tail forms—come from the whole corpus.

Disassembly was performed on Horsey.exe (4,374,528 bytes, x86-64 PE). All code addresses given in this thesis are build-specific and must be re-anchored against a different executable build before use; the re-anchoring procedure is described alongside each address in Chapter 12.

1.4 Terminology

  • u32, i32: 4-byte little-endian unsigned/signed integers.
  • f32: IEEE 754 single-precision float.
  • u8, u16, u64: 1-, 2-, 8-byte little-endian integers.
  • String: a u32 byte length followed by that many bytes of UTF-8, no terminator.
  • Genome: 240 bytes, one per gene, each packing two alleles.
  • HDR: world-item header size, 41 for v9–12, 45 for v8.
  • S: HDR − 41, so 0 for v9–12, 4 for v8.
  • yoff: shorthand for tableEnd + 0x38, the vial-world entrance Y anchor.
  • EXTRA: per-location tail bytes beyond the owner block.

Chapter 2: Top-Level Layout and the Header

2.1 The File Skeleton

The file begins with a 0x14-byte header, followed by the record table, the global player block (0xF0 bytes), the someCount array, the map block (W × H, RLE tiles), the buried-item block, the world-item block, the location block (indexed), and a 20-byte trailer. Every block chains exactly. Nothing in the load path scans for a pattern. The live save1.dat (440,624 bytes, v12) accounts for every byte from 0 to EOF.

0x00  header                        <- version, record count
0x14  record table                  <- every named entity
      global player block (0xF0)    <- money, inventory, vial-world entrance
      someCount array
      map block (W x H, RLE tiles)
      buried-item block
      world-item block              <- horses, Truck, location markers, ground items, holes
      location block (indexed)      <- names, stabled horses, interiors, owners, Bookies
      20-byte trailer               CONFIRMED (ownerFlag=0 + 16B vial payload, 6.10)

All integers are little-endian. u32/i32 are 4 bytes, f32 is an IEEE single, u8 is one byte. A string is a u32 byte length followed by that many bytes of UTF-8, with no terminator.

2.2 Header Fields

version     = u32(0x00)             // 8..12
rngSeed     = u64(0x04)             // xorshift64 PRNG seed (2.2a)       RE_CONFIRMED
cycleIndex  = u32(0x0C)             // cyclic array index, wraps at a fixed size  RE_CONFIRMED
recordCount = u32(0x10)

2.2a The Header’s Non-Version Fields

Bytes 0x04–0x0B are a single u64, not two independent dwords. The record-table writer (0x1400c8240) writes them with one WRITE_U64 call. The value comes from global 0x1403F45C0, the xorshift64 PRNG state—specifically the seed, a u32 from a time/entropy source zero-extended to u64. That is why u32(0x08) is “usually 0”: the upper half starts at zero and only becomes non-zero after many xorshift iterations.

Byte 0x0C is a cyclic array index maintained by 0x1400c7a20: it reads the index, increments it, and wraps to 0 when it reaches the element count of a small fixed array (0x1403F45D8..E0). The corpus observation “small counter, grows with playtime” matches a cyclic step-per-event index.

An editor should carry these values verbatim from the source file rather than inventing them. The PRNG seed governs every rand() call the game makes after loading (coat patterns, adornment jitter), so changing it changes the visual appearance of every horse.

2.3 Record Table

off = 0x14
repeat recordCount times:
    nameLen = u32(off)
    name    = utf8[nameLen]
    fixed   = 18 bytes
    n       = u32(off + 4 + nameLen + 18)
    links   = n dwords                    // offspring (children) — RE_CONFIRMED (2.4)
    off    += 4 + nameLen + 18 + 4 + n*4
tableEnd = off

One entry per named entity. The 18-byte fixed block is DERIVED:

+0   u8   flags: 0x01 rename on load, 0x02 Championship Horse, 0x04 GMO Horse,
                 0x08 Diving Medal, 0x10 Strong Horse Medal, 0x20 Trampoline Medal,
                 0x40 Acrobat Medal
+1   u8   name colour
+2   u8   races participated
+3   u8   regular races won
+4   u8   sumo wins
+5   u8   name colour copy (redundant copy of +1; 0xFF for NPCs)  RE_CONFIRMED
+6   i32  parent A record index (-1 = none)
+10  i32  parent B record index (-1 = none)
+14  u32  reserved (always 0; no runtime reader)  RE_CONFIRMED

Bit 0x01 makes the game rename the horse on load. That is how a new stable horse gets a name the game chooses rather than one you invent.

The modal value is 00 00 00 00 00 00 FF×8 00 00 00 00—24,850 of 171,309 corpus records, and the only common one that reads as nothing has happened to this horse yet. Note what it is not: no record in the corpus is all-zero, hence a zeroed block is a shape the game has never written. Clone a real one rather than synthesising it.

A horse points at its record with the recordIndex i32 in its detail block (Section 9.3). -1 means unnamed, which is normal for wild horses (574 of 576 on-map in the reference save) and a state the game never writes for a stabled one (Section 6.3).

2.4 Pedigree — Bidirectional Link Structure

The n link dwords at the end of each record entry are offspring (children), not siblings or lineage. The structure is bidirectional:

  • Child → parents: fixed-block +6 (parentA, i32) and +10 (parentB, i32) point from a child record to its two parents. -1 means no parent.
  • Parent → children: the trailing n dwords list each child’s record index.

At runtime, both directions live in the record struct: parentA at +0x48, parentB at +0x4c, and children as a std::vector<i32> at +0x70 (begin_ptr at +0x70, end_ptr at +0x78, capacity_ptr at +0x80). RE_CONFIRMED by disassembling both the writer (0x1400c8240: lea rcx,[rdi+0x70]; call 0x140075980) and the reader (0x1400c84d0: lea rcx,[rbx+0x70]; call 0x1400762e0).

The loader trusts the stored offspring list. The record table reader (0x1400c84d0) reads the children vector directly from the save file via 0x1400762e0 (reads count then each i32 into the vector). The post-read callback (0x1400c7dd0) performs only a name-string copy—no consistency check against parent pointers, no rebuild of children from parentA/parentB indices. An editor MUST keep both directions in sync manually: when adding a new child record with parentA=X, also append the child’s index to record X’s link list (and similarly for parentB=Y).

2.5 Appending a Record

A record’s identity is its ordinal position in the table, and every reference to one is that ordinal: a horse’s recordIndex, and another record’s parent links. Hence:

  • Appending at tableEnd renumbers nothing. Indices 0..n-1 keep their meaning and the new entries take n, n+1, …. Write recordCount at 0x10 and splice the entries in at tableEnd.
  • Inserting anywhere else silently repoints every horse in the file. No length field disagrees, the table still walks, and every name after the insertion belongs to the wrong horse. There is no reason to ever do it.
  • Parent links do not survive a move between files. An index harvested from save A points at whatever sits at that position in save B, so anything importing a fixed block from elsewhere must clear both parent dwords to -1.

3.2 Complete Byte Coverage

Disassembly of the save writer (0x14006db90) and reader (0x14006e380) accounts for every byte of the 0xF0-byte block. The write sequence after the record table is: 7 × u32, 1 × f32, 3 × u32, 3 × u32→bool, 1 × u32, 1 × u32→bool (always 0), 1 × u32, 1 × u32→bool, 1 × f32 pair (8 B), 1 × u32, then the 6-slot inventory loop (72 B), then the 13-pair loop (104 B) = total 0xF0.

Field identifications. Traced from game state struct offsets to their consumers: +0x04 (year) and +0x10 (sleeps) are confirmed by the format string "< Simulation Paused - Year %d Sleeps %d Races %d >" at 0x140307F98. +0x14 (Money) is confirmed by the constructor’s default of 50 and add [rax+0x308], 0x3E8 (+1000) on a race win. +0x18 (tutorial step) is confirmed by the constructor: −1 when tut is disabled, 13 when enabled. +0x3C (annual win flag) is set to 1 when the year-end championship condition is met and cleared to 0 after the prize is paid out.

Boolean format. Fields marked u32→bool are written as 4-byte dwords (0 or 1) and read back with (val == 1)—the reader consumes 4 bytes per boolean. The field at +0x28 is always written as 0 (the writer passes xor ecx, ecx) and the reader stores it to a discarded local, so it is a dead field in the current version.

The 13 dword pairs at +0x88..+0xEF are the race leaderboard—{losses, wins} per player slot. Slot 0 is the local player, slots 1–12 are the NPC players. Written by 0x140105F10 on every race finish: position codes 5/6 (top-2 finishers) increment the win counter B[slot]; all other finishes increment the loss counter A[slot]. The leaderboard display at 0x14006C180 sorts by wins descending, losses as tiebreaker.

Money comes from a controlled pair: beforeupgrade.dat → afterupgrade.dat shows 49874 → 49374 across one 500-credit Truck upgrade, with no other dword in the block moving in a matching way.

Vial-world entrance is confirmed against the Tiled map, whose vial world object sits at x=576, y=800. Tiled anchors gid objects at the bottom-left, so y − 32 = 768, and every unmodified save reads exactly 576.0 and 768.0. Files that differ (concept.dat, abandoned.dat) were built from edited maps. This is the anchor the shorthand yoff refers to: yoff = tableEnd + 0x38.

Chapter 4: Map, Buried Items, and World Items

4.1 Block Chaining

someCount = u32(tableEnd + 0xF0)
stride    = version >= 12 ? 8 : 6                  // RE_CONFIRMED: 4×u16 for v12, 3×u16 for v8-v11
mapStart  = tableEnd + 0xF0 + 4 + stride*someCount + 8
W, H      = u32(mapStart - 8), u32(mapStart - 4)
<RLE tile stream, W*H tiles>
mapEnd
buriedCount = u32(mapEnd)
buried[i]   = { u32 cell, u32 itemId }              at mapEnd + 4 + 8*i
buriedEnd   = mapEnd + 4 + buriedCount*8
wordLength     = u32(buriedEnd)                     // RE_CONFIRMED: a container name string (12.4)
worldCountOff  = buriedEnd + 4 + wordLength + 8
worldItemCount = u32(worldCountOff)
worldItemStart = worldCountOff + 4

The someCount stride is RE_CONFIRMED: the save writer always writes 4 × WRITE_U16 per entry (game struct stride 0x24 = 36 bytes, fields at +4, +8, +0xC, +0x10 within each entry). The reader gates the 4th u16 on version >= 12 (cmp dword ptr [version], 0xc; jl skip).

Map pixel coordinates are tile * 32, and world y is (row + 1) * 32—the map’s own row 0 sits at y 32.

4.2 The RLE Tile Stream

Tiles run left to right, top to bottom. Read the first byte of each entry and branch on it:

first byteentrytile
0x3B–0x3E1 byteshorthand for family 0, id first − 0x3A (Plain1…Plain4), no fences, no growth
0x3F2 bytesa water run: repeat = next byte tiles of family 6, id 9
anything else2 or 3 bytesfam = first & 0x3F, fenceT = first & 0x40, fenceL = first & 0x80, id = next byte, and a third growth byte when id >= 0x47

Writing it back:

  • A water run caps at 255 per entry, so a longer run emits repeated 0x3F FF pairs.
  • Family 0 with id 1–4 and no fences takes the one-byte shorthand.
  • The border ring is forced to family 15 on every write, whatever the grid holds.
  • Re-encoding is lossless but not byte-exact against an arbitrary save, because the game’s own writer makes different run-splitting choices—about 150–160 bytes shorter per file. A file this editor wrote does round-trip exactly.

4.3 Buried Items

Each entry is a cell index and an item id. cell is row * W + col, with the same row offset as everything else: x = (cell % W) * 32 and y = floor(cell / W) * 32 + 32. Item ids follow the range in Section 6.2.

A buried item is three values in a packed stream. It is not a world-item record, which is why it cannot carry a genome—there is no record to put one in.

4.5 Tile Family and Tile Id Must Agree About Growth

A tile is [flag][id], plus a third growth byte when it carries growth. The decoder in Section 4.2 decides that byte from the id (id >= 0x47). The family in flag & 0x3F states the same fact, and across 129 corpus files the two never disagree:

familiesids
1, 2, 3, 9, 10, 11, 12 (grass, ngrass, bog, acacia, apple, palm, cactus)always id >= 0x47, growth byte present
every other familyalways id < 0x47, no growth byte

So fam=1 / id=1—GrassLand’s family with Plain1’s id—is a byte pair (01 01) the game’s own writer never emits, and one the game cannot read: it takes the growth byte from the family, so it consumes a third byte the encoder did not write and every tile after it shifts by one. The map desynchronises and the save will not load.

Nothing else shows it. The file parses, walks and re-encodes byte-identically in any decoder that keys on the id, which is why this needs an explicit check. A dedicated validation predicate taking (fam, id) is that check, wired into three places: a warning on load, a block on any export that would re-encode the map, and a per-file row in a batch verification pass.

It shipped once. An editor’s paint palette defaulted to { fam: 1, id: 1 }, so painting before clicking a swatch wrote exactly this pair. bad-save.dat carries two such tiles at (124,118) and (121,120) and is the only file in the corpus that does. Repair is a one-byte write per tile—flag 0x01 → 0x00, same length, nothing downstream moves.

Chapter 5: Location Identity

5.1 Numeric Id from Tiled gid

Location identity is a hard numeric id taken straight from the Tiled gid. It is not derived from the name. Only the name record’s byte position is found by the indexed array of Section 6.1, and pairing names to markers by index is exact.

Every location on the map is a type-2 world item, and its index byte at start + 5 is the location’s id. Across the whole corpus:

type-2 index  ==  Tiled gid − 97

97 is firstgid for the locs.tsx tileset in the Tiled map. On the near-vanilla start.dat and newsave.dat, pairing markers sorted by index against the name records in file order reproduces 26 of 26 of the map’s location objects, matching both the object type and its tile-centred coordinates exactly.

A marker is tile-centred: x = col*32 + 16, y = row*32 + 16. My House at (3056, 3696) is col 95, row 115. Row 0 therefore gives y = 16, not 32—a location marker does not follow the horse rule of (row+1)*32.

5.2 Reading a gid Out of the Atlas

locs.tsx is referenced by the map but is not present in the data folder—the game reads the gid numerically and never loads the .tsx. The gid is a tile-grid index into locs.png, not the sprite’s ordinal position in the atlas XML:

locs.png is 256 x 256 with 32 x 32 tiles  ->  8 columns
gid = 97 + (sprite.y / 32) * 8 + (sprite.x / 32)

The c="N" attribute says how many consecutive tiles the family covers (LocStable c="8" → gids 97–104). Counting <sprite> entries instead gives the wrong answer for everything after the first: LocTrack is the second entry but sits at y="32", hence it starts at gid 105.

Two caveats about the sprite names:

  • LocSweetie and LocPaddock are swapped relative to how the game uses them. Gid 111 (LocSweetie by position) is type="paddock", and gid 125 (LocPaddock by position) is type="sweetie". The type string in the Tiled map is authoritative, the atlas name is not.
  • Gids 105–109 fall inside the LocTrack c="6" range but are the five procedurally-named stables (…'s Hideaway, …'s Equestrium, …'s Estate, …'s Grange, …'s Horsery). Only gid 110 is the Race Track.

5.3 Ordinal Pairing Is Wrong

Pairing the n-th name record with the n-th type-2 marker in world-item order does not work. The world-item block stores markers in spawn order, not index order, and 91 of 107 corpus files have the two disagree. On save1.dat 29 of 30 come out mislabelled—the marker at (3024, 3952), which is type="bobs", gets called “My House”.

Sort markers by index before zipping, or better, key on index directly.

Chapter 6: The Location Block

6.1 An Indexed Array

worldItemEnd:
    <12 bytes padding>
    for index = 0, 1, 2, ...:
        u32  present            0 = slot empty, 1 = a record follows
        <location record>       only when present == 1
    <the `unknown` record>      terminator, outside the index space

index is the same identity as in Chapter 5. The array is dense over the index space and a skipped slot costs one zero dword.

The array has a fixed length, and it is version-dependent: 48 slots (0–47) on v11 and v12, 38 slots (0–37) on v8, v9 and v10. Checked against every walkable file: 125 v12 and 4 v11 saves at 48, 13 v8–v10 saves at 38. 48 is every gid from 97 up to but not including the Truck’s 145, which is exactly the range locs.png reserves for locations. RE_CONFIRMED: the save writer loops 0x180 / 8 = 48 iterations hard-coded (cmp rsi, 0x180).

The X/Y pair here is a redundant copy of the type-2 marker’s coordinates—identical in 1,955 of 2,003 location instances, with all 48 exceptions in tool-built or degenerate files. An editor that moves a location must write both, or the two drift apart. That dual-write is what keeps them in sync, so it has to stay.

The dword before interiorCount is a crowd ordinal—RE_CONFIRMED as a “selected entity index” by the container serializer (0x14006d520). The serializer iterates the crowd vector and writes the index of the entry matching a selectedEntity pointer (container+0x148), or 0xFFFFFFFF when nothing matches. It names one of this location’s own stabled horses, with 0xFFFFFFFF for “none”. Over 3,268 location records:

What an editor must do with it: never invent one, and never leave a stale one. Emptying a crowd, or shrinking one below the stored ordinal, has to write “none”. A still-valid ordinal must be left byte-for-byte alone, because 889 loadable records say “none” and 2,381 name a horse, so the value is not a function of the count and overwriting a live one invents state.

An earlier draft read this field as ownerState—0 when the tail carries an owner, 0xFFFFFFFF when it does not. That rule has 54 corpus violations, including files the game loads happily. Owner presence correlates with the field only because a location with no proprietor usually has no crowd either.

The interior list’s stride is therefore HDR + 8—53 bytes on v8 and 49 on v9–12, plus 240 when the flag is set. Hard-coding 49 desynchronises every v8 save with interior items.

A ground item’s coordinates are map pixels. An interior item’s are room units, the same scale as a stabled horse’s position (Section 6.3), and the same 0…20 range applies.

Item ids run 0–95, but only 0–48 (ItemHay … ItemMemory) are objects the game places. Past 48 they are decorations, inventory icons and power-up glyphs. Ids 26–46 are the wardrobe subset a horse can wear.

The +15+D u16 is a per-item usage counter—RE_CONFIRMED by disassembly of the serializer (0x14006d9a0), a setter at 0x14005ce60 (reads the type’s default from the item property table at 0x1403d5e70), and a decrement-and-deplete path at 0x14005d5c6: dec [rbx+0x44]; jg keep; mov [rbx+0x11], 1; jmp remove. When the counter reaches zero the item sets its depletion flag (entity+0x11 = 1) and is removed from the world. N hay bales or carcasses on the ground are still N separate type-3 records, each with its own counter.

The halfW and halfH values at +41+D and +45+D are saved but immediately overwritten after loading by 0x14005caa0, which recomputes them from the sprite database. The saved bytes are redundant; writing zeroes there would produce the same loaded state.

6.3 Stabled Horses — Exact

The horse that goes missing from your ranch. A conditional slot at the end of every stable’s tail:

6.8 Clide’s Rides — The Car Counter

tail + 244, the last dword of the record, is the number of cars the lot has generated. It is the only field in that tail that ever varies, and across the corpus it takes exactly {0, 2, 4, 6, 8}—never higher, matching the reported cap of 8. It does not track the interior item count, so it is a running total rather than current stock.

The same “one small counter at the end of the tail” shape appears elsewhere—Sweetie’s House tail+244 (0–8), O’er Yonder Acres tail+244 (0–3), Lasso-Mart tail+244 (0–3)—so the slot is reused for whatever that location generates.

6.9 The Bio-Hacker Vat Matrix

The largest tail in the file, and it decodes cleanly:

tail+0            u32    ownerFlag
tail+4            240    owner genome
tail+244 .. +275  8 x u32 counters      (tail+268 = the set-cell count, below)
tail+276 .. +4115 960 x u32             the availability matrix

960 = 240 genes × 4 bases, in gene-major order, every dword 0 or 1. A base becomes available to the simulation once you feed the vat a horse carrying it.

Three independent confirmations. The arithmetic closes exactly: 4 + 240 + 32 + 3840 = 4116. Under the gene-major reading a vat is either empty (all 240 genes at 0) or has every gene at 1 to 4—never 5, and in the corpus never a mix—which would be impossible by chance if the layout were wrong (richest save: 908 of 960 set, 191 genes at 4, 46 at 3, 3 at 2). And u32(tail + 268) equals the number of set cells in every file that has a Bio-Hacker—a built-in checksum, and a free validity gate for any write to this region. That also makes the counter read-only on its own: editing it without the matrix breaks the invariant.

Correction. This paragraph used to say “every gene has 2 to 4 bases set”, which held for the richest save only. The 84-file corpus: 59 vats entirely empty; in the 25 non-empty ones, genes at 1/2/3/4 = 4,153 / 1,453 / 285 / 109, and no gene at 0. Feeding adds the bases on both strands (user-confirmed): a gene where the fed genome carries the same base twice gains one cell, which is why 1 is common after only a genome or two. The empty-or-full rule has rare exceptions in play (user report); the corpus has none.

Column k is the base’s index in the gene’s n priority string—the same 0-based index the genome byte packs (n1/n2 minus 1), not ACGT order. Confirmed by a controlled probe (beforevatprobe.dat → aftervatprobe.dat): an empty vat was fed one genome whose even genes were homozygous for n[3] and odd genes n[3]/n[2]. Result: 360 cells set = 120 genes at 1 + 120 at 2; every even gene gained exactly column 3 whatever the letter (A 30, C 26, G 29, T 35 genes), every odd gene exactly columns 2 and 3; 191 genes decisive for priority order, 0 for ACGT, 0 inconsistent with both. Only the matrix and tail+268 changed—the other seven counters were identical before and after.

6.10 The unknown Record

The last location record in every file is named unknown, sits outside the index array, and has coordinates (0, 0). On save1.dat it carries crowd = 6 and 146 interior items. It is the vial world’s interior—an interior with no map exit, which is why its coordinates are zero and why its entrance position lives in the global player block instead (Chapter 3).

The bytes after the unknown record are its tail. The tail is exactly 20 bytes in every corpus file (verified: tailEnd == fileSize with 0 bytes after in 100% of files). The layout is:

A hard guard prevents both from being set simultaneously (if [+0xAC] != 0, skip the +0xAD write), which is why the corpus never has both set.

9.4 The Owner and Champion Containers Have No Detail Block

A location tail’s owner and champion genomes are followed by the location’s own tail fields, not by a horse detail block. Reading detailOff + 6/7/9 there returns whatever the tail holds: across the corpus the “age” of an owner ranges to 120 and its “personality” to 255, which is exactly what garbage looks like.

So anything that writes a horse’s age, personality, status or worn items must exclude those two containers by construction, or it will write into a location’s counters. The map, stabled, Bookie and Lost Horse containers all have a real detail block and are safe.

Chapter 10: The Genome

10.1 Encoding

240 bytes, one per gene, in raw gene-id order. The same block appears in a horse record, in a location tail, and inside a type-3 item that carries DNA.

Each byte packs a pair of alleles—RE_CONFIRMED by disassembling the genome encoder at 0x14006d380. The game stores alleles at runtime as 0-based indices (0..3) in two 240-byte strands at entity +0x2B8 (dominant) and +0x3A8 (recessive). The encoder loops 40 iterations × 6 genes and for each gene computes (strand_B[i] + 1) << 3 | (strand_A[i] + 1), which is the same n2 * 8 + n1 formula with 1-based indices. A gene’s n attribute in the gene definitions is a 4-letter priority order, e.g. "ATCG":

byte  = n2 * 8 + n1                    n1, n2 in 1..4
pair  = n[byte % 8 - 1] + n[(byte - byte % 8) / 8 - 1]

Only 16 byte values are therefore legal, and they are the codeSet:

9, 10, 11, 12, 17, 18, 19, 20, 25, 26, 27, 28, 33, 34, 35, 36

A byte outside that set is not a genome byte. This is the cheapest structural check in the file: a 240-byte run entirely inside codeSet is a genome, because codeSet is 16 of 256 values and nothing else matches by chance. 0 is not legal, so a zeroed genome is corrupt rather than blank.

10.2 Genome Hash

The u32 immediately after the genome—at genomeStart + 240, the first half of the 8-byte gap—is a genome hash, not a per-horse identity. Within a file, every duplicate group turns out to be horses that share a genome, 576 of 576 in the reference save. Across 109 unrelated saves, 18,730 of 18,736 distinct genomes (99.97%) map to exactly one value—a lineage or session id could not agree across unrelated files, but a hash must.

Carry the hash with the genome, and never invent one. Copying one horse’s genes without its hash leaves the copy carrying the donor’s hash for genes that are no longer the donor’s. That state is tolerated—it is what any gene edit already leaves an existing horse in, and such files have been loading and playing for a long time, which is itself the best evidence the game recomputes the hash on load—but writing a random value there is simply wrong.

10.3 Trait Expression

The trait value a gene expresses comes from its g values and its m dominance percentage in the gene definitions: m >= 100 means the dominant allele wins outright, and below that the two blend by percentage. That is presentation rather than format—the file stores only the pair.

For the text format the tools exchange (HH:SEQUENCE, two lines per helix, zero-padded), the 240 genes group into 20 helices by a fixed table carried in the tools’ gene-data module.

Chapter 11: If You Are Writing an Editor

The short list of things that will bite you, each with its section:

  1. Never insert into the record table anywhere but the end (Section 2.5). Nothing will complain and every name after the insertion will belong to the wrong horse.
  2. Clear parent links on any record block copied between files (Section 2.5).
  3. Key locations by the type-2 index byte, not by name or by ordinal (Sections 5.1, 5.3).
  4. Keep the present-flag array at its full length (Section 6.1). Shortening it crashes the game, and index 37’s tail is the trap that causes it (Section 6.4).
  5. Write both copies of a location’s coordinates (Section 6.2).
  6. Write “none” to the crowd ordinal when a deletion empties or shrinks a crowd past it—and leave a still-valid one alone (Section 6.2).
  7. Seed a new location with at least the crowd the game is observed to write (Section 6.10a).
  8. Read an item’s id and coordinates through the DNA flag (Section 6.2). The payload is spliced in at +12, and a record whose length is right can still have every field read from the wrong place.
  9. Use HDR + 8 for the interior stride, not a hard-coded 49 (Section 6.2).
  10. Anchor a tail field on EXTRA, not on tail (Section 6.4), and bound a tail-anchored one against what follows it rather than against tailEnd (Section 6.5a).
  11. Check family against id on every tile you write (Section 4.5).
  12. Carry a genome’s hash with the genome (Chapter 10), and refuse a genome with a byte outside codeSet.
  13. Do not write detail-block fields on an owner or champion (Section 9.4). They have no detail block.
  14. Clamp a room coordinate you invent, and leave the ones already in the file (Section 6.3).
  15. Preserve the PRNG seed at 0x04–0x0B (Section 2.2a). Changing it changes the visual appearance of every horse. Carry it verbatim from the source file.

12.4 Location Serialization — Virtual Dispatch

Each location’s tail is written by a virtual method at vtable + 0xB0. The container serializer (0x14006d520) writes the common structure (name, crowd, interior items, coordinates, owner flag + genome), then the save writer calls [vtable+0xB0] for the location-specific tail. Different location types (My House, Race Track, Bio-Hacker, etc.) each have their own implementation.

The unknown record’s virtual serialize (vtable+0xB0) is the last write before the file is flushed, so the 20-byte file trailer is part of its output.

Chapter 14: Conclusion

14.1 Summary of Contributions

This thesis has presented a complete structural, semantic, and reverse-engineered analysis of the Horsey Game save file format. The principal contributions are:

  1. A complete byte-level map of the save file, from header to trailer, accounting for every byte in the live reference save.
  2. A confidence taxonomy distinguishing STRUCTURAL, DERIVED, OPEN, and RE_CONFIRMED claims, enabling future researchers to assess the reliability of each assertion.
  3. The record table structure, including the bidirectional pedigree link system and the critical rule that records may only be appended, never inserted.
  4. The global player block (0xF0 bytes), with all fields decoded and confirmed by disassembly and controlled experimentation.
  5. The RLE tile stream encoding, including the family/id growth agreement rule that, when violated, desynchronises the entire map.
  6. The indexed location array, version-dependent (48 slots on v11/v12, 38 on v8–v10), with the present-flag structure and the critical warning about index 37’s tail length.
  7. Location identity as a hard numeric id from the Tiled gid, with a complete index → location mapping.
  8. The location record body, including crowd, interior items, coordinates, and the crowd ordinal with its strict editorial rules.
  9. The per-location tail system, with the owner flag, EXTRA table, and four special cases (My House, Race Track, stables, Bubber’s Hutch).
  10. The Bookies, the Lost Horse, the Bio-Hacker vat matrix, and all other location-specific data structures.
  11. The 240-byte genome encoding, with the codeSet validity check and the genome hash.
  12. Player inventory, Truck upgrades, and horse detail blocks.
  13. A set of editorial imperatives for any tool that reads or writes the format.
  14. A catalogue of reverse-engineered code addresses for the save I/O path.

14.2 Implications for Game Preservation

The Horsey Game save format is a case study in bespoke serialization: tightly packed, version-dependent, intolerant of desynchronization, yet entirely decodable through systematic reverse engineering. The format’s design reflects the game’s needs—equine genetics, location state, world persistence—without the overhead of general-purpose frameworks. For preservationists, this thesis provides the means to read, verify, and migrate saves across versions, and to repair corrupted files.

14.3 Future Work

Several avenues remain open:

  • My House’s 240-byte payload: the 60 floats stored there are likely world-state or progression data, but their meaning is not yet established. Recovering the original 480 bytes by reversing the genome packing is a first step.
  • Bubber’s Hutch’s six strings: these parse fully, but the riddle’s in-game behaviour needs observation to confirm the semantics.
  • The Jockey Club’s stub serialize: the 44-byte tail in tool-built saves is an artifact, but its origin could be traced.
  • Version migration: the format changed between v8 and v12 (someCount stride, HDR size, slot count). A complete migration guide would be valuable for preservation.
  • The someCount array: its four u16 fields are written and read, but their semantic meaning is not fully documented here.

14.4 Final Remarks

The Horsey Game save file is a dense, precise artifact. Every byte has a purpose, every offset is load-bearing, and every deviation from the game’s own writer is a potential crash. This thesis has aimed to document the format so completely that a reader can write a correct editor from it alone—and so that future researchers can build on its findings without re-deriving them. The format rewards careful study: it is a window into the game’s architecture, a testament to the craftsmanship of its developers, and a challenge to anyone who would modify it. For the PhD candidate whose professor is a devoted Horsey Game fan, this thesis offers not only a technical reference but a tribute to the game’s enduring complexity.
